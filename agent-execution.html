1. 总体链路

主 Agent 不直接处理终端输入，也不直接实现每个工具。它位于 Runtime、UI、模型 API、工具系统和 SessionStore 的交界处：UI 负责一轮的生命周期，Agent 负责消息和模型/工具循环，Runtime 负责把依赖注入进去。

1 个主 Agent维护当前会话的 messages、todos、usage、checkpoint 和上下文估计。
1 个 turn checkpoint每条用户请求开始时创建，文件编辑可回滚；Bash 外部改动不在代码 checkpoint 内。
同一套核心循环交互式 REPL 和 print/non-interactive 使用同一个 Runtime 与 Agent。
main()解析参数、选择模式
→
createRuntime()配置、prompt、tools、hooks

App.onSubmit()分类输入、建立 turn
→
Agent.run()消息与模型/工具循环

核心不变量：一次 turn 内不会并发启动两个 Agent.run()；模型没有 tool call 时才可能结束，有 tool call 就把工具结果写回消息并再次调用模型。

2. 启动与模式选择

入口

bin/claude-pro.js 负责启动进程或 supervisor，真正的参数解析和模式选择在 src/main.js。

  1. 处理配置命令与 --self-check。
  2. 读取 system-prompt 文件、解析 --continue/--resume。
  3. 读取 restart state，判断 stdin/stdout 是否是 TTY。
  4. TTY 进入 runRepl()；非 TTY 或 --print 进入 runPrint()。

当前实际模式

main()
  ├─ interactive TTY  → runRepl()
  └─ non-TTY/--print  → runPrint()
边界：当前 main.js 不再解析 --headless 或 --remote-id，因此旧文档里通过 VirtualTerminal 启动后台 host session 的入口并不是当前可达路径。

兼容参数 --remote-control/--rc 可以被接受，但不会重新打开旧的网页控制通道。

3. Runtime 构建

src/runtime.js:createRuntime() 把 Agent 需要的依赖一次性组装完成。Agent 本身只消费抽象回调和工具，不负责寻找配置文件或创建终端界面。

输入与配置

加载配置、trace、当前模型和 effort，寻找 shell，确定工作目录、平台、日期以及 gateway provider。

上下文

组合主 system prompt、CLAUDE.md、AGENTS.md、项目/用户指令、memory、MCP、模型和 Git 初始快照。

执行能力

创建 CheckpointStore、hooks、MCP、BackgroundTasks、工具 registry 和主 Agent。

System prompt 的来源

prompt override / saved prompt
  + mainSystemPrompt()
  + 环境、平台、shell、cwd、日期、Git snapshot
  + 项目/用户/本地指令文件
  + auto-memory index
  + MCP instructions
  + 当前 model / effort 相关信息

prompt provider 是惰性的并带缓存。恢复会话时只有 prompt fingerprint、append suffix 和 model 都兼容，才复用保存的 system prompt；日期变化会把提醒放进下一条用户消息，而不是强制重建整个 prompt。

4. 一轮请求如何执行

交互式路径的 UI 生命周期在 src/ui/repl.js 中，Agent 的消息和模型循环在 src/agent.js:Agent.run() 中。

  1. 输入分流：App.onSubmit() 先识别 peer 消息、队列文本、slash command、图片、?、!、# 和普通 prompt。
  2. 领取 turn：startTurn() 同步设置 busy，防止两个 Agent.run() 并发；随后回显用户消息、异步生成标题、处理图片和 @file 附件。
  3. 准备 Agent：Agent.run() 执行日期提醒、effort boost、idle cleanup、UserPromptSubmit hooks、后台任务通知和 pending reminders。
  4. 建立 checkpoint：CheckpointStore.beginTurn() 为这一轮创建文件快照边界。
  5. 写入用户消息：pushMessage() 更新 messages、activity、context accounting，并通过 IO 回调持久化和发布 UI/远程事件。
  6. 进入模型/工具循环：自动压缩（如果需要）→ 调模型 → 保存 assistant message → 有 tool call 就执行工具并回写结果 → 再调模型。
  7. 结束 turn：没有工具调用且没有待验证/待续写/待 hook 轮次时结束；最后清 busy、完成 peer 任务并排空队列和后台通知。

Agent 主状态机

Idle等待用户输入或后台通知。
Preparinghooks、reminder、checkpoint、prompt。
Streaming消费模型 SSE，积累 text/thinking/tool input。
ToolRunning执行工具、发布 progress、形成 tool_result。
Compacting摘要旧上下文并替换 transcript。
Verifying编辑后运行验证；失败可反馈模型。
Waiting等待本地问题、队列或后台任务。
Done/Error写入 session、清理 busy、显示结果。

5. 模型请求与 SSE

callModel()

  1. 降低历史图片体积。
  2. 取得当前 system prompt 并通过 io.systemPrompt() 持久化一次。
  3. 规范化 transcript，修复未完成/孤立/重复 tool result。
  4. 构建 model、messages、tools、cache bucket、effort 请求参数。
  5. 调用 streamAgentRequest()，更新 context token 估计。

gateway 请求

src/api.js:buildParams() 使用 Anthropic Messages 格式、stream:true、工具 schema、可选 thinking/effort 和 cache-control。

请求带 X-Claude-Code-Session-Id。GPT 模型由 gateway 的 Codex 路径处理；不兼容的 Codex 签名 thinking block 会在发送给 Claude 模型前清掉。

SSE 事件归约

message_start
  → content_block_start
  → text_delta / thinking_delta / input_json_delta
  → content_block_stop
  → message_delta
  → message_stop
  → assistant message + usage + cost + stop_reason

流式事件同时被 Agent、终端 renderer 和远程 transcript 发布器消费。没有最终 stop event 或 stop reason 会视为错误；中断时保留已有文字并估算已产生的输出。

6. 工具调度、验证和副作用

src/agent.js:runTools() 先按工具类型调度，再由 runOne() 完成单个调用的完整生命周期。

并发规则

  • 连续的只读工具可并行，例如 Read、Glob、Grep。
  • AskUserQuestion 不参与并行。
  • 写文件、Bash 和其他有副作用的工具顺序执行。
  • 中断后未执行的调用会得到解释性错误结果。

runOne() 顺序

  1. 解析工具名和 JSON 输入。
  2. 校验必填字段、primitive 类型和工具专属约束。
  3. 执行 PreToolUse hooks。
  4. 编辑前记录文件 snapshot，发布 tool-start。
  5. 执行工具、处理图片结果和 progress。
  6. 执行 PostToolUse，保存过大的输出，统计成功编辑。
  7. 返回 Anthropic tool_result。
当前没有独立 permission prompt 层。工具是否执行由 schema 校验、工具自身校验、hooks、abort 和 checkpoint 共同决定。
工具类别当前行为边界
文件Read 记录 freshness；Write/Edit 会在执行前进入 checkpoint。需要先读过文件或处于有效 freshness 状态。
Bash非交互子进程，支持 timeout、abort、cwd、截断和 full-output 文件。shell 直接改文件不进入代码 checkpoint。
SearchGlob/Grep 优先使用 ripgrep，失败时回退 JavaScript scanner。输出仍受工具结果和上下文清理规则影响。
Web可产生额外 gateway 请求，WebFetch 可能调用独立摘要请求。side request 默认不静默等待长限流窗口。
Task前台任务嵌套 Agent；后台任务立即返回 task id。后台任务有独立 abort signal 和 completion notification。

7. 上下文维护与压缩

自动 compact 条件

shouldAutoCompact() 要求：自动压缩开启、消息数超过 2、连续失败少于 3 次、context estimate 超过阈值，并且确实有新的上下文增长。

compactOnTheWay() 在请求前执行；如果请求仍能放下而 compact 失败，可以继续；连续三次失败后关闭自动 compact；如果请求已经过长则重新抛错。

摘要与替换

requestSummary() 先使用当前模型、system prompt、tools、effort 和独立 cache bucket 生成摘要；响应调用工具或格式不对时回退到 SUMMARY_SYSTEM。

compact() 用 continuation message 替换旧 transcript，刷新 system prompt、清 file-read state、重置 context/compaction counters，并发布完成事件。

长时间空闲后的清理

大约 65 分钟无活动后，Agent 可以清理旧 tool result：保留最后五个可清理结果；大型非 Read 结果写入 tool-results 文件；被清掉的 Read 结果之后必须重新读取。必要时还会移除旧 thinking block，保证 API transcript 合法。

恢复会话的两层语义：完整 loaded.messages 会进入 Agent/model context；终端只显示最近一段消息以避免刷屏。compact 后，旧 raw transcript 由 continuation summary 替代，这是设计行为。

8. 持久化、恢复、重启和 rewind

SessionStore

会话保存为：

<CONFIG_DIR>/projects/<sanitized-cwd>/<session-id>.jsonl

JSONL 记录包含 meta、message、reset、topic/name、cost/cache metadata 和 saved system prompt metadata。

loadSession()

  1. 加载 JSONL 并替换当前 SessionStore。
  2. 恢复 topic、name、cost、cache timing、messages。
  3. 重建 file state、activity 和 context estimate。
  4. 兼容时复用 saved system prompt。
  5. 恢复远程状态并打印最近 transcript。

Checkpoint 与 rewind

每个用户 turn 一个 checkpoint。每个文件在本 checkpoint 内只保存一次原始内容，支持代码和会话、仅会话、仅代码三种 rewind。会话 rewind 会截断 Agent.messages 并重置 todo/context；代码 rewind 保留对话，但插入重新读取受影响文件的提醒。

进程重启

restart state 会保存 session、model/effort、todos、draft/cursor、队列、checkpoint snapshot、restart loop 时间、peer identity 和 remote id。新进程恢复后可自动提交 continuation note 和排队消息。

9. 子 Agent 与后台任务

Sub-agent

runtime.spawnSubagent() 创建独立 Agent 和独立 message history，共享配置、model、hooks、checkpoint 基础设施，但接收过滤后的工具集，并受最大深度限制。

子 Agent 的 usage 合并回 parent；失败会连同部分 assistant text 返回。

BackgroundTasks

run_in_background 的 Task 拿到独立 abort signal，立即返回 task id；完成后标记 completed/failed/killed，并转成主 Agent 可消费的 notification。

主 Agent 可以等待、读取输出，或用 TaskStop 终止后台任务。

不要混淆两类 background：后台 sub-agent/task 当前可达；旧版持久化 host session（--headless --remote-id、VirtualTerminal、网页启动后台会话）仍有 legacy 文件，但当前入口解析器不会把它们接入执行路径。

远程 transcript 事件

当前 reducer 支持 user、output、流式 text/thinking、tool、progress、sub 和 done。长文本和工具输出会在 snapshot 中裁剪，snapshot 受条目数和大小限制。

RemoteControl 的职责

  1. POST /v1/remote/sessions 注册会话。
  2. 打开 commands SSE；断线指数退避，404 时重新注册。
  3. 按顺序发送 event batch，必要时发送完整 snapshot。
  4. 发布状态、viewer count、bye 和 peer 消息。
  5. 关闭时发送 final bye。
当前命令边界：RemoteControl 只处理 viewer 更新、snapshot 请求和 terminal-to-terminal peer。浏览器发来的 send、interrupt、dialog、options、suggest、list、output 等旧控制帧会被忽略；网页不回答本地 dialog。

11. 错误、重试、限流和中断

APIError

统一保存 HTTP status、retryable、prompt-too-long、overload、retry-after 和 rate-limit 信息。

可重试

无 status、408、409、429 和 5xx。401/402 会转成 gateway-specific message。

可中断

模型请求、rate-limit wait、Bash、后台任务都绑定 abort signal。

重试策略

src/ratelimit.js 区分快速 429、已知 reset window、未知 reset、529 overloaded 和 exhausted retry budget。等待期间保持可 abort，并发布 retry、rate_limit_wait、rate_limit_resume、reset 等事件。

Agent 层的错误分流

  • abort：保留部分 assistant text，返回 interrupted turn。
  • promptTooLong：进入一次必需 compact。
  • 工具失败：通常变成模型可见的 tool_result，不直接终止整轮。
  • 不可恢复错误：交给 REPL 或 print 层显示并结束当前 turn。
  • REPL 的 finally：完成 peer task、清 busy/rate-limit、发送排队内容。
